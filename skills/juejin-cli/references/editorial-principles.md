# 技术文章写作原则

每篇能独立阅读：开头交代项目、具体问题与读完能得到什么。项目介绍适合在开头提供真实界面截图、安装官网和开源仓库入口；避免用链接堆砌替代正文。

平台会单独显示文章标题，正文直接进入引言，无需再放同名一级标题。CLI 会移除开头与标题完全一致的一级标题，其他标题保持原样。

先检查素材，再选结构。只有故障日志时可以写一次排障；有可运行的最小实现时可以写教程；有多种方案和取舍时可以写设计分析。不要为了套模板虚构踩坑经历、性能数据或对比结论。

段落服务于读者的问题。章节可以合并、删除或改变顺序；短文章无需分出背景、方案、验证、总结四大部分。用具体的因果关系解释设计，少用抽象评价。专业术语首次出现给出简短解释，保留准确的技术名称。

图解释代码难以直观表达的关系，代码展示图无法表达的关键细节。优先使用 draw.io 技能，保留源文件并导出图片；不要为了凑数量放装饰图。代码只截取支持论点的部分，较长实现链接到源码。

完成后核对：标题是否准确；第一段能否独立理解；关键主张是否有代码、数据或实测依据；图与正文是否一致；命令是否能执行；哪些步骤尚未验证。把限制写在对应结论旁边。

文章末尾可以停在一个清楚的结论、适用边界或真实的下一步，不必重复全文，也不强制预告下一篇。整体语气像向同事解释自己的工作，保持具体、坦诚、有信息量。
